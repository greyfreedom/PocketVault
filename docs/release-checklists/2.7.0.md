## Compatibility and data-safety gate

- [ ] Install the Play-signed candidate over an official 2.6.0 installation containing a schema 3 vault with passwords, secure notes, payment cards, custom fields, TOTP entries, categories, and attachments.
- [ ] Unlock without writing, then change a generator setting and confirm an automatic encrypted backup precedes the first schema 4 commit. Also verify entry and TOTP edits can perform the first upgrade.
- [ ] Repeat the first-write upgrade with synthetic schema 1 and 2 vaults, preserving all supported data.
- [ ] Restore the pre-upgrade backup and verify its data; confirm schema 4 vaults and backups are rejected by 2.6.0 without mutation.
- [ ] Force an automatic-backup or staged-commit failure and confirm the original vault remains unchanged.
- [ ] Export and restore a schema 4 backup; verify the rule library, independent templates, and last mode and composition, including fixed text and unfinished drafts.
- [ ] Confirm early V2 authenticated migration still succeeds with the master password and that V1 remains rejected without mutation.

Use synthetic credentials and disposable test data only. Never test a release candidate against the sole copy of a real vault.

## Device and store checks

- [ ] Test new-vault setup, unlock, wrong-password handling, background auto-lock, master-password change, biometric setup/reset, export, import, and automatic-backup retention.
- [ ] Combine all four rule types; verify fixed text, letter case, allowed symbols, confusing-character exclusions, Unicode length, and rejection of compositions with no randomness or more than 128 output code points.
- [ ] Add, duplicate, edit, and reorder many fragments without a fragment-count cap. Check dragging the first visible card, scrolling, and accessibility move actions.
- [ ] Create, update, load, and delete templates; verify library edits do not change template snapshots and deleting a template preserves the active composition.
- [ ] Confirm “View existing templates” opens the template list and “Clear current rules” appears below “Save as template”, clears the active composition, and leaves saved rules and templates intact.
- [ ] Close and reopen the page, relock, and restart the app; verify the last mode, template association, and actual rule order. Switch to random mode and back, including with an unfinished composition.
- [ ] Confirm results clear on lock, old callbacks cannot overwrite a new session, and settings-save failures offer a retry.
- [ ] Verify copy actions and system text-selection copying in results and editors use the sensitive clipboard and timed clearing.
- [ ] Verify layout, keyboard access, and controls in all seven locales and with large text.
- [ ] Recapture Google Play and project-site generator screenshots for the new rule interface.
- [ ] Paste and review [`../release-notes/2.7.0.md`](../release-notes/2.7.0.md) in Play Console; review Data safety, privacy-policy URL, content rating, target API, app access, and store contact details.

## Publication and traceability

- [ ] Replace `Unreleased` in `CHANGELOG.md` with the actual publication date.
- [ ] Commit the final candidate, then run `./scripts/tag-release.sh` to create, verify, and push signed tag `v2.7.0` from that exact commit.
- [ ] Build and upload the signed `googlePlayRelease` AAB, then record its SHA-256 digest.
- [ ] Download the Play-generated signed Universal APK from the same bundle record.
- [ ] Verify version, package, Play App Signing certificate, offline manifest, and hashes with `scripts/publish-github-release.sh`.
- [ ] Publish the GitHub Release from `v2.7.0`, attaching only the Play-generated Universal APK.

Do not publish a locally generated APK signed with the upload key, debug key, or any certificate other than the official Play App Signing certificate.
